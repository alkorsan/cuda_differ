2026.10.03 (4th release, by @alkorsan)
+ feature: WinMerge's directory-listing call. The user's profiling
  showed the remaining 8 s was pure listing latency (9 x scandir
  open ~200 ms each + ~33 entry reads ~117 ms each, all in the
  walk) while WinMerge compares the same folders instantly. The
  WinMerge source (Src/DirTravel.cpp, LoadFiles) revealed why: it
  lists with FindFirstFileEx(FindExInfoBasic, ...,

  WHOLE directory and skips the 8.3 short-name lookup -- where
  Python's os.scandir uses plain FindFirstFileW with a small buffer
  (a fresh round trip every few entries). The plugin now calls the
  exact same Win32 API through ctypes on Windows: one bulk round
  trip per directory, size/mtime/attributes read straight from
  WIN32_FIND_DATAW. Silent fallback to os.scandir everywhere else
  (other OS, long paths, API unavailable, unexpected error) -- the
  scandir path is unchanged and always correct.
+ change: barrier-free parallel walk. The pool previously scanned
  in breadth-first WAVES (a wave waited for ALL its directories);
  now a directory's subfolders are submitted the moment its own
  listing arrives (FIRST_COMPLETED), like WinMerge's notification-
  queue-fed worker pool. No scan ever waits behind an unrelated
  slow directory; the wall time approaches the longest CHAIN of
  directories plus one listing latency.
+ docs: profiling notes now say explicitly how to MEASURE speed:
  enable_profiling ON + enable_cprofile OFF (clean section report
  AND the scan stays fully parallel; the cProfile layer forces the
  serial scan on purpose, so profiled runs are always slower than
  real runs). Also documented: comparing freshly copied/extracted
  folders competes with the antivirus's background scan of those
  very files -- the classic signature is the FIRST tree walking
  several times slower than the second, identical one (the user's
  walk_left 4.5 s vs walk_right 1.2 s).

- fix: switching CudaText sessions (the Sessions menu,
  app_proc(PROC_LOAD_SESSION), session-manager plugins) no longer deletes
  the compare tabs' tracking info from settings/cuda_differ2_state.json.
  The session manager closes the old session's tabs to replace them, and
  those closes used to hit on_close's unregister path, killing the
  persisted registrations of tabs that were not really closed -- they
  still exist in the session file being left and come back when the user
  returns to it. The plugin now brackets the load with CudaText's new
  APPSTATE_SESSION_LOAD_BEGIN_PRE event (the only one that fires BEFORE
  the load's first on_close_pre / on_close -- APPSTATE_SESSION_LOAD_BEGIN
  arrives only after the closes, too late; the SESSION_SAVE_BEFORE and
  SESSION_SAVE_AFTER events cannot tell a switch from the ~40s auto-save):
  _session_loading is raised on BEGIN_PRE, and every on_close inside the
  window keeps the tab's persisted entry (the runtime teardown still
  runs -- the editor object is genuinely destroyed; the app-exit flag
  outranks the session-loading flag). On APPSTATE_SESSION_LOAD the
  re-attach pass _restore_session_tabs -- the body of on_start2, now
  shared by both call sites -- re-attaches the loaded session's restored
  compare tabs (per-tab sessions, toolbars, title colors, scroll set,
  dead-record cleanup) exactly like a restart; on APPSTATE_SESSION_LOAD_FAIL
  only the flag is cleared (the pass's dead-record cleanup must not run
  against an uncertain session state). readme documents the behavior in
  the "Compare tabs, restarts and session switches" chapter.

- fix: compare colors no longer leak from the ORIGINAL published Differ
  plugin into Differ 2 when both are installed and the original ran a
  compare first in the same CudaText session. Root cause, verified in
  the CudaText/ATSynEdit sources: bookmark kinds are APP-GLOBAL slots
  (bookmark(BOOKMARK_SETUP, nkind, color) overwrites that kind's color
  for the whole app, and ATSynEdit resolves every bookmark2 line's
  background through it), and both plugins registered kinds 24/25/26 --
  the original re-registers them with ITS theme colors on every compare
  it runs, and Differ 2's config cache (settings mtime / theme names)
  then had no reason to re-run its own BOOKMARK_SETUP, so every later
  Differ 2 compare painted the original's colors. Fixes:
  * the kind numbers move to the top of CudaText's 1..63 clamp range
    (deleted/added/changed -> 61/62/63), far from the small numbers
    plugins usually pick;
  * the editor tags move off the original's 148/149 (DIFF_TAG -> 4082,
    ignored-gap tag -> 4083), so each plugin's clear-by-tag no longer
    wipes the other's marks when both paint the same editor;
  * kind registration moves out of get_config() into the new
    _register_bookmark_kinds(), which Command.__init__ calls at plugin
    load and config() calls unconditionally before every compare --
    re-registration is self-healing (even a future kind collision with
    yet another plugin repairs itself on the next compare), and
    get_config() is side-effect free again.

- fix: removed the wrong assumption, stated in several comments and
  enforced by dead code, that an untitled tab must be PROP_MODIFIED=True
  for CudaText's session saver to back it up. That rule holds for FILE
  tabs (their text is only stored in the session when modified) but NOT
  for untitled tabs: DoOps_SaveSession ALWAYS stores an untitled tab's
  text -- it forces 'modified' to true for them in the session file,
  with the same rule for the first and the SECOND half of a split --
  and DoOps_LoadSession brings untitled tabs back as modified whatever
  the flag was. Code removed: on_close's app-exit branch no longer puts
  the compare halves back to PROP_MODIFIED=True before the session
  write (the exit 'Save tabs?' dialog has already run by the time
  on_close fires, and the flag never gated untitled text anyway -- the
  restore was a no-op). Comments corrected in on_close_pre (the halves
  are modified as a side effect of being filled with content, not to
  stay in the session; clearing the flag on clean tabs cannot drop
  either half from the session) and on_save_pre (PROP_MODIFIED is left
  untouched because it plays no role in session persistence -- its only
  real job is driving the 'Save changes?' dialogs). The NECESSARY
  PROP_MODIFIED uses stay: on_close_pre clearing the flag on clean
  compare tabs (suppresses the 'Save changes?' close dialog),
  compare_clip_sel clearing it on the two scratch tabs before closing
  them (same dialog suppression), and _sync_to_original_by_id marking

+ add: the char-level tokenizer of the native diff engine is now
  configurable -- the new option differ2.algorithm.break_chars (config
  dialog, "algorithm" chapter, right after "Detailed comparison")
  holds the word-break characters the engine was hard-wired to until
  now. The default is WinMerge's "Word break characters" options
  default ".,:;?[](){}<=>`'!"#$%&^~\|@+-*/" (period, comma, colon,
  semicolon, question, brackets, parens, braces, angle brackets,
  equals, backtick, quotes, hash, dollar, percent, ampersand, caret,
  tilde, backslash, pipe, at, plus, minus, asterisk, slash). WinMerge
  research behind this: the engine's stringdiffs.cpp Init() hard-codes
  only the small fallback ",.;:" that runs until SetBreakChars() is
  called, but WinMerge's Options dialog stores the long list above as
  the setting's default and pushes it into the engine on every
  compare -- so the long list is the effective default, and the plugin
  (and the CudaText diff_proc default) mirror it; an earlier unreleased
  draft of this option used ",.;:" under the assumption it was
  WinMerge's default.
  Every character of the string is its own token and a word boundary
  inside the char-level highlights: with the default, "v1.2.3" splits
  into "v1" "." "2" "." "3". The engine refines every changed region
  by trimming its common prefix/suffix, so a SINGLE change inside a
  word highlights only the changed characters no matter the set
  ("v1.2.3" vs "v1.2.4" gives the same "3"/"4" highlight with any
  break chars); the set decides whether equal punctuation inside a
  region with SEVERAL changes acts as an anchor that splits it:
  "v1.2.3" vs "v1.9.4" highlights the two digits separately with the
  dots unpainted by default, but as one "2.3"/"9.4" block (dots
  included) with an empty set; "v1.2.3" vs "v1-2-3" highlights only
  the two "."/"-" swaps by default (the dash is in the default set),
  but the whole ".2."/"-2-" with a set that has no dash, e.g. ",.;:".
  An empty string disables punctuation breaking (words split on
  whitespace only); adding characters that are not in the default
  (e.g. "_" for snake_case identifiers) breaks words on yet more
  punctuation. Whitespace,
  CR/LF and (with "Ignore numbers" on) digits are classified before
  the break-char check, so listing them has no effect; non-ASCII
  characters always break words regardless. The value flows from
  settings/cuda_differ2.json through Command.get_config (sanitized by
  the new differ_native.normalize_break_chars -- a hand-edited
  non-string value falls back to the default instead of failing every
  compare, since the engine accepts strings only) onto the Differ
  (diff.break_chars, set by refresh_compare next to diff.ignore_flags),
  and from there into ALL THREE DIF_CHARS call forms: the batched
  background job (differ_native.start_async_char_diff), its
  synchronous fallback (sync_char_diff) and the legacy single-pair
  path (Differ._char_diff) -- one value per whole batch, exactly like
  the ignore bitmask. The line-level diff (DIF_TEXTS) is not affected:
  break chars only tune which characters the char-level details
  highlight inside already-changed lines, never which lines are
  changed. The option is native-only like the five ignore options
  (the pure-Python algorithms break words at every punctuation
  character, so the setting means nothing to them): its OPTS_META
  entry carries the new generic 'native_only' flag, and

  Python algorithm is the effective one (configured Python algo, or a
  native one that fell back because cudatext.diff_proc is missing),

  CudaText build whose diff_proc API takes the break_chars parameter
  (the 5_add_differ_api branch with the break-chars patch); no
  backward compatibility is kept -- older builds lack the parameter
  and the DIF_CHARS calls fail, the engine and the plugin are updated
  together.

2026.08.06 (by @badrelmers)
+ add: new "vscode" diff algorithm (default), ported from VS Code's diff implementation (https://github.com/microsoft/vscode/tree/main/src/vs/editor/common/diff). Uses dynamic programming (O(MN) LCS with equality scoring and consecutive-diagonal bonus) for files with fewer than 1700 combined lines, and Myers diff (O(ND) with snake optimization) for larger files. Also includes VS Code's heuristic post-processing: optimizeSequenceDiffs (shift/join adjacent diffs to natural boundaries) and removeVeryShortMatchingLinesBetweenDiffs (absorb tiny equal blocks between large changes). The equality scoring (1 + log(1+line_length) for exact matches, 0.99 for whitespace-only matches) and consecutive-diagonal bonus are the key innovations that make this algorithm produce correct alignment on files with many duplicated lines where both patience diff and difflib fail. The "vscode" algorithm is now the default; "patience" and "difflib" remain available as alternatives.
* change: replaced the boolean "use_patience_diff" config option with a new "diff_algorithm" option (frm='str2s', dct=[('vscode','VS Code (DP + Myers)'), ('patience','Patience Diff'), ('difflib','Python difflib stdlib')]) that exposes a real dropdown in the config dialog. The default is now 'vscode' (previously the boolean defaulted to false, i.e. difflib, then later 'patience'). differ.py reads self.diff_algorithm and selects VSCodeSequenceMatcher / PatienceSequenceMatcher / DefaultSequenceMatcher accordingly.

2026.08.03 (by @badrelmers)
- fix: "Diff with file..." / "Diff with tab..." commands now honor the "autojunk" config option. Previously difflib.unified_diff was called without autojunk (it does not expose the parameter, see https://github.com/python/cpython/issues/118150), so the unified-diff path always used autojunk=True regardless of the user setting. When autojunk is True (the default), we now call difflib.unified_diff directly so the hot path stays on stdlib code; only when the user sets autojunk=False do we fall back to a small local _unified_diff wrapper (verbatim copy of difflib.unified_diff + an autojunk kwarg). Chose this over monkey-patching SequenceMatcher via unittest.mock.patch -- avoids pulling a testing tool into production code, avoids globally patching a stdlib class for the duration of the call, honors autojunk=True as well as False, and stays forward-compatible if CPython ever adds autojunk to unified_diff (we just delete the wrapper and call difflib.unified_diff(..., autojunk=...) directly in both branches).
